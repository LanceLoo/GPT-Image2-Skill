# OpenCode 自定义服务生图与编辑

本仓库根目录的 `SKILL.md` 是唯一的 Skill 入口，面向 OpenCode 使用，也可通过 OpenChamber 发起请求。当前在仓库内开发，不安装或移动到全局目录。开发完成后，可以将整个仓库放入 `~/.agents/skills/` 下的一个子目录，保留根目录 `SKILL.md`、`skills/` 和 `src/` 的相对结构。

启动脚本只加载本仓库源码；源码缺失时直接报错，不调用已安装的其他版本、PATH 中的命令或上游远程包。`tests/` 等开发文件可以继续保留。

## 配置来源

CLI 的 `--opencode-provider "<provider-id>"` 从全局 `~/.config/opencode/opencode.json` 或 `opencode.jsonc` 读取配置；设置 `XDG_CONFIG_HOME` 时使用该目录下的 `opencode/`。两个文件同时存在或都不存在时，必须用 `--opencode-config` 指定。`<provider-id>` 是用户配置中的实际服务标识，不是固定名称或界面显示名称。

支持 `provider[provider-id].options.baseURL/apiKey`，以及 `providers[provider-id].settings.baseURL/apiKey` 两种配置结构。支持 `{env:变量名}`，不支持 `{file:...}`。只读取一个文件，不模拟 OpenCode 多层配置合并，不读取认证存储。指定 OpenCode provider 时不读取 `.env`，不回退到其他 Key 或官方地址。

URL 保留已有 `/v1` 前缀，SDK 生图时追加 `/images/generations`，传入 `-i` 时追加 `/images/edits`。所选服务必须兼容 OpenAI Images API，并支持所请求的图片模型；能够调用聊天模型并不代表支持生图，生图成功也不代表编辑可用。已在一个配置的服务上完成生图和单图无蒙版编辑验证，其他服务、路由和版本需自行确认兼容性；这不是稳定性保证。

## 首次验证（PowerShell）

在仓库根目录运行；`uv` 首次运行会安装脚本依赖：

```powershell
uv run .\skills\gpt-image\scripts\generate.py --opencode-provider "<provider-id>" --model gpt-image-2 -p "一只橘猫坐在窗台上，温暖日光，简洁插画，无文字" --size 1024x1024 --quality medium -n 1 -f .\outputs\first-image.png
```

如需指定配置，在命令中追加 `--opencode-config "配置文件的绝对路径"`。运行前确认输出文件不存在。成功后会打印图片路径，可在本机打开验证。

如果代理的安全规则禁止访问配置或凭据，应由用户在自己的终端执行此命令；不要让代理包装或改写命令规避限制。无需在聊天中提供真实 Key。

API 失败不会自动重试；指定 OpenCode provider 时只报告错误类型和 HTTP 状态，避免网关响应回显凭据。404 通常需要确认路由，401/403 需要确认认证或权限，400 需要确认服务支持的参数。不要仅根据状态码判定根因。

## 文字生图前的轻量澄清

根目录 `SKILL.md` 的“生图前的轻量澄清”由 Agent 编排，不是新增 Python 问答逻辑或独立文本模型调用：

- 需求存在影响结果的关键歧义时，优先用 `question` 集中询问，默认一轮 1～2 个问题，并提供贴合需求的方向建议及自由补充空间。没有该工具时用聊天提问。用户等待、取消或没有有效回答时不发送图片请求。
- 需求明确、前文已确认或用户要求直接生成时，跳过创意提问；一句话也可以足够明确。不重复收集已有信息，不强制选风格、图库或重新确认默认参数。provider 等必要执行前提仍需满足。
- Agent 忠实整理用户要求和已选建议，将最终提示词交给 CLI 的 `-p`；CLI 本身不会扩写。按原文使用时不改写，默认不翻译或添加未选择的创意。用户已要求生成并回答问题后，不再机械地增加一轮生成确认；讨论或预览不视为调用授权。
- 该策略减少意图歧义，不保证消除图片模型随机性，也不解决网关错误或尺寸不遵循问题。仅用于文字生图，图片编辑继续使用下述 Render 流程。

行为验收应覆盖：模糊需求只问关键问题；明确需求及按原文请求不被打断；已确认信息不重复询问；取消或仅讨论不触发调用；回答后的提示词只包含用户约束和已选方向。可先在不发送图片请求的条件下检查提问和最终提示词；离线 CLI 测试不能证明 Agent 在宿主中一定遵循这些问答规则，真实端到端生图仍需用户授权。

## 单图编辑与 OpenChamber 交互

在同一启动命令中加 `-i "输入图片绝对路径"` 即使用编辑接口，`-p` 改为用户确认的修改要求，`-f` 指向新的输出文件。根 Skill 当前只编排单图、无蒙版编辑；CLI 虽有多图和 mask 参数，不代表该工作流或所选服务已经验证这些能力。尺寸等参数是请求值，仍需核对输出文件，不能保证兼容服务严格遵循。

OpenChamber 面板的建议、输入框和等待/取消流程见根目录 `SKILL.md` 的“OpenChamber Render 编辑面板”。这是 Agent 的操作规范，不是新增前端、后台服务或 CLI 子命令：

- 面板使用宿主提供的 `openchamber_render` 和 `awaitAnswer: true`，通过 `openchamber.submit` 交回选择，再由 Agent 执行本地 CLI；HTML 不接触凭据或直接请求图片接口。写入 Skill 并不让其他客户端自动获得此工具。
- 无视觉能力时仍可基于原始提示词及修改历史提供建议，必须声明未检查实际图片；文件检查与视觉理解分开。文件不可用时不能编辑，没有视觉能力本身不妨碍将有效图片传给编辑接口。
- 按当前工具的单提交按钮约定，建议先填入可修改指令，编辑或取消经统一按钮确认；不能把多个按钮的本地演示当成已接通的提交能力。没有 Render 时使用聊天确认。
- 一次明确提交最多执行一次编辑；取消不请求接口、不删除图片。等待期间不自动执行，用户可改在聊天框发消息；不保证未说明的超时、断线恢复或请求撤回能力。

以下离线测试验证 CLI 和凭据契约，不覆盖宿主的 Render 提交、等待或刷新行为；这些交互仍需在宿主中验证。交互验证应先只提交取消，或检查编辑提交数据后暂停，不发送真实图片请求；需要端到端编辑时先取得用户的调用授权。
